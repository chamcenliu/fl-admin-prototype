# Freelog Admin 原型全局交互规范

本规范用于统一 Freelog Admin 原型及后续后台页面的交互行为、信息组织和验收口径。适用范围包括页面树、管理后台业务页、列表页、详情页、创建/编辑页、弹窗、批量操作和 PRD 标注。除非业务需求明确说明，新增页面应遵循本规范。

## 1. 交互原则

### 1.1 清晰优先

- 页面只保留当前任务所需的信息和操作。
- 同一类操作使用统一名称，例如“新建”“编辑”“停用”“恢复”“删除”“查看详情”。
- 操作结果必须可感知：状态变化、成功提示、错误提示或页面跳转至少出现一种反馈。
- 不使用颜色作为唯一状态信息；状态同时展示文字。

### 1.2 同类功能使用一致的打开方式

- 同类型或相似功能模块、页面必须采用一致的打开方式，避免同一类操作在不同页面中分别使用弹窗、抽屉或独立页面，造成认知和操作成本差异。
- “新建 XXXX”和“编辑 XXXX”属于同一类创建/编辑操作时，必须使用相同的承载方式，并保持表单结构、操作区和返回路径一致。
- 满足以下任一条件的新建/编辑表单，必须使用独立页面承载，不得使用弹窗或抽屉：
  1. 被新建或编辑的对象是当前页面的核心条目或主列表条目，例如“授权策略模板管理页”中的“新模板”和已有授权策略模板。
  2. 被新建或编辑的条目配置较多，属于长表单，表单输入控件数量大于或等于 5 个。
- 只有少量字段的辅助配置、确认操作或预览操作才可以使用弹窗，例如预览、删除确认和批量修改适用范围；同一业务对象的“新建”和“编辑”仍应保持打开方式一致。

### 1.3 保持上下文

- 列表进入详情页后，应保留返回列表的明确入口。
- 独立新建/编辑页不展示单独的“返回列表”按钮；使用页面标题区右上角的“取消/保存”操作完成返回，并在返回前正确处理未保存变更。
- 弹窗关闭后回到触发弹窗的原位置，不重置用户已经填写的其他筛选条件。
- 批量操作完成后保留当前筛选条件，并清空已选择项。
- 需要跨页面查看的内容，优先使用页面内标签切换或明确的“返回”动作。

### 1.4 防止误操作

- 删除、停用、恢复、扣除、拒绝、批量变更等有业务影响的操作必须二次确认。
- 二次确认文案说明对象、动作和结果，例如“确认停用该奖励吗？停用后将不再生成新的发放记录。”
- 不可逆操作使用危险色按钮；可恢复操作使用普通主按钮或次按钮。
- 保存前离开存在未保存修改时，应提示保存、放弃修改或继续编辑。

## 2. 全局页面结构

### 2.1 页面框架

后台页面统一采用以下结构：

1. 左侧全局导航：按业务域分组，当前页面高亮。
2. 顶部栏：展示当前用户或系统身份，保留全局返回、分享或全屏能力。
3. 页面标题区：展示业务域、页面标题、简短说明和主要操作。
4. 页面主体：由筛选区、统计区、列表区、详情区或表单区组成。
5. 反馈层：Toast、确认弹窗、错误提示、空状态和加载状态。

### 2.2 导航

- 一级导航使用业务域名称，例如“用户”“资源”“交易”“运营”“安全与合规”。
- 二级页面使用对象加动作命名，例如“活动奖励管理”“内容审核策略管理”。
- 当前页面必须同时在左侧导航和页面标题中体现。
- 导航切换不应修改已保存数据；未保存编辑状态需要先触发离开确认。
- 页面树中的页面 ID、标题和实际页面入口保持一致。新增页面需同步更新 `src/mockData/pageTree.ts` 和业务导航数据。
- 第三级页面的页面内业务面包屑统一使用“业务域 · 业务对象”结构；末级业务对象使用文字链接返回对应的业务管理页，不再重复放置同义的返回按钮。

## 3. 页面标题区和操作优先级

页面标题区左侧依次放置业务域、标题、说明，右侧放置主要动作和辅助动作。所有独立新建/编辑页均在页面标题区右上角放置“取消/保存”，不再展示“返回列表”按钮，也不在页面底部重复展示操作区。

按钮优先级统一为：

| 优先级 | 样式 | 使用场景 |
| --- | --- | --- |
| 主要操作 | 实心主按钮 | 新建、保存、确认、发布、审核通过 |
| 次要操作 | 描边按钮 | 筛选、重置、返回、查看记录 |
| 行内操作 | 文本操作按钮 | 编辑、详情、停用、恢复 |
| 危险操作 | 危险色文本或按钮 | 删除、扣除、拒绝、封禁 |

同一页面主要操作一般不超过两个。页面标题区不放与当前任务无关的快捷动作。

## 4. 列表页规范

### 4.1 筛选区

- 搜索框放在筛选区左侧，支持名称、编号、用户或业务关键字搜索。
- 枚举型条件使用下拉框，默认值为“所有”或“全部状态”。
- 时间范围使用统一的起止时间控件，展示格式为 `YYYY-MM-DD HH:mm`。
- “重置”清空所有筛选条件并恢复默认值。
- 筛选结果数量放在筛选区右侧，展示当前结果数，不使用无法解释的模拟总数。
- 筛选条件变化后立即刷新结果；如果查询成本较高，可使用“查询”按钮，但页面内必须保持一致。

### 4.2 表格

- 表头使用业务字段名称，字段顺序按用户决策顺序排列：识别信息 → 关键属性 → 状态 → 操作。
- 第一列可使用复选框做批量选择；表头复选框表示当前筛选结果的全选/取消全选。
- 核心名称或编号可以使用文本链接进入详情或编辑。
- 状态使用“文字 + 状态色 + 状态点”展示，状态颜色遵循：成功绿色、待处理橙色、危险红色、中性灰色。
- 单元格内容过长时截断显示，悬停展示完整内容；不影响主要字段识别。
- 行内操作超过三个时使用“更多”菜单或拆分到详情页。
- 无结果时展示空状态，并说明是“暂无数据”还是“筛选无结果”；提供“重置筛选”动作。

### 4.3 批量操作

- 选择一条或多条数据后，在表格上方出现批量操作栏。
- 批量操作栏展示“已选 N 条”，并提供对应动作和“取消选择”。
- 批量停用、恢复、删除、审核或扣除必须统一确认。
- 批量操作完成后反馈成功数量和失败数量；失败项不能静默丢失。

## 5. 表单页规范

### 5.1 表单布局

- 独立新建/编辑页统一由页面标题区和分组表单主体构成；标题明确展示“新建 XXXX”或“编辑 XXXX”，表单按业务阶段组织。
- 表单按业务阶段分组，例如“基础信息”“关联配置”“发放规则”“高级设置”。
- 标签使用业务名称，必填项使用 `*`，选填项不强制添加冗余文字。
- 输入控件下方放置帮助说明、单位或格式要求；说明不替代字段标签。
- 相关字段尽量同组排列；两个短字段可使用两列，长文本和规则配置使用整行。
- 新建/编辑页面的内容区域应自适应浏览器可用宽度，优先填充主工作区；不得因固定窄宽度在右侧留下大块空白。需要控制阅读宽度时，应以主工作区为上限，并在窄屏下继续自适应。
- 同一横向分组中使用同类型控件时，控件高度、边框和内边距必须统一；辅助按钮或说明不得撑高输入控件，横向字段保持顶部对齐。
- 同类型控件在无特殊业务说明时，默认复用全局统一的高度、字体、边框、圆角、内边距和交互状态；不得仅因所在模块或排列方式不同而单独改变样式。
- 不同页面或模块中的同类型单行控件（如输入框、下拉列表框、日期选择器和搜索框）在无特殊业务说明时，默认使用统一的控件高度、内部文案字号、行高、内边距、边框和圆角；按钮或辅助操作不得改变相邻同类控件的高度。
- 表单字段数量达到 5 个，或涉及核心业务对象时，使用独立创建/编辑页面，不使用窄弹窗或抽屉承载。
- 同一类对象的新建和编辑必须使用相同的打开方式；若满足核心条目或长表单条件，两者均使用独立页面。
- 短操作、确认操作和少量字段配置可以使用弹窗。
- 长列表或需要持续维护的业务内容使用独立页面承载；从页面发起的少量筛选、选择或批量添加操作可以使用弹窗，并在关闭后回到原页面位置。

### 5.2 校验

- 校验在失焦或提交时触发；必填校验在提交时必须完整执行。
- 错误信息紧邻错误字段，说明如何修正，例如“请输入奖励额度，支持最多两位小数”。
- 提交失败时保留用户已填写内容，并在表单顶部展示错误摘要。
- 编号、名称等唯一性字段需要在提交前提示重复；不能仅依赖后端错误文案。
- 数字字段拒绝非法字符，金额、次数、额度必须显示单位。

### 5.3 保存与离开

- 保存按钮固定使用“保存”或“保存并发布”，避免使用含义不清的“确定”。
- 保存成功后返回来源列表，并通过 Toast 告知结果；编辑失败留在当前页面。
- 所有独立新建/编辑页将“取消/保存”统一放在页面标题区右上角，并移除单独的“返回列表”按钮。
- 页面底部不重复展示“取消/保存”操作区，避免同一操作出现两个入口。
- 点击“取消”时，如果当前页面没有未保存变更，直接返回来源列表。
- 点击“取消”时，如果当前页面存在未保存变更，使用统一确认弹窗提示用户处理修改：选择“保存并返回”则先执行完整校验，保存成功后返回列表，保存失败则留在当前页面；选择“不保存并返回”则放弃变更并返回列表；选择“继续编辑”则关闭提示并保留当前页面和已填写内容。
- 该操作位置和取消逻辑适用于当前原型全部同类页面，也适用于未来新增的独立新建/编辑页。

## 6. 弹窗与反馈

### 6.1 弹窗

- 弹窗必须有明确标题、关闭入口和主次按钮。
- 关闭按钮位于右上角，点击遮罩默认不关闭包含未保存内容的表单弹窗。
- 确认弹窗主按钮文案使用具体动作，例如“确认停用”“确认审核”，不使用泛化的“确定”。
- 弹窗内容过长时使用内部滚动，不让页面整体横向溢出。
- 弹窗内的选择列表，确认操作统一放在列表底部，使用“添加”和“取消”；不在筛选区或列表上方重复放置同一确认动作。

### 6.2 Toast 与状态反馈

- 成功：说明完成的动作，例如“活动奖励已保存”。
- 失败：说明失败原因或下一步，例如“保存失败，请检查奖励编号是否重复”。
- 危险操作的失败不能只使用短暂 Toast，必要时在页面内保留错误状态。
- 加载中显示按钮禁用或 loading 状态，防止重复提交。

### 6.3 空、加载和错误状态

- 加载状态保持页面结构，避免内容突然跳动。
- 空状态包含说明和下一步动作，例如“暂无活动奖励，先新建一个奖励”。
- 网络或服务错误包含重试入口；本地原型可以使用明确的模拟错误提示。

## 7. 业务状态规范

状态命名应稳定、互斥、可解释。推荐使用以下状态：

| 状态类型 | 推荐文案 | 颜色 |
| --- | --- | --- |
| 正常运行 | 正常、进行中、已上线、已启用、已发放 | 绿色 |
| 待处理 | 待审核、未生效、即将开始、待领取 | 橙色 |
| 结束或关闭 | 已结束、已停用、已拒绝、已扣除、已关闭 | 红色或灰色 |
| 中性 | 草稿、未配置、暂无数据 | 灰色 |

业务动作与状态变更必须匹配：

- “停用”只能作用于可运行对象，完成后状态变为“已停用”。
- “恢复”只能作用于已停用对象，恢复后进入明确的可运行或未生效状态。
- “审核通过”将待审核记录变为已发放或待领取；“拒绝”必须记录拒绝原因。
- “扣除”必须二次确认，并记录扣除原因和操作人。

## 8. 活动奖励管理交互约定

- 奖励列表支持按奖励类型、奖励状态、名单生成方式筛选，并支持按奖励名称、编号、关联活动搜索。
- 创建/编辑活动奖励按“基本信息、奖励信息、发放规则、奖励互斥规则、是否审核”分组；至少包含奖励组、编号、名称、关联活动、备注、奖励类型、额度、说明、有效期、领取方式和名单生成方式。
- 手动添加名单需要配置统一发放时间和获奖用户名单；系统根据发放时间默认生成“发放时间前 30 分钟至发放时间后 30 天”的有效期。获奖名单管理使用独立页面，添加获奖用户使用弹窗完成筛选和添加；选择列表应同时展示用户标签、最近登录和账号状态等识别信息。奖励信息区提供“编辑”入口返回当前奖励编辑页。
- 自动生成名单需要配置一个或多个发放条件组、条件组之间的组合关系、完成次数和可选的发放次数限制；有效期由管理员直接配置。
- 开启“发放前需要审核”后，相关记录必须进入“活动奖励发放记录”的待审核状态。
- “查看发放记录”从具体奖励条目进入记录页，发放记录必须按奖励编号隔离展示，不能混入其他奖励的记录；记录页保留返回奖励管理入口。
- 发放记录页在列表前展示当前奖励信息；自动生成奖励展示昨日发放额度、次数、用户数及累计发放额度、次数、用户数，手动添加奖励展示累计发放额度和用户数。
- 发放记录支持按待审核、已发放、已拒绝、已扣除筛选；审核通过、拒绝和扣除均需有明确反馈。
- 发放时间前的锁定规则、有效期结束规则和奖励互斥规则需要在字段旁说明，避免只依赖内部约定。

## 9. 原型工程约定

- 页面业务数据集中维护在 `src/mockData`，不要在 JSX 中散落重复的模拟数据。
- 新增业务页面优先拆分为独立组件，页面专属样式放在同名 CSS 文件中。
- 页面树、后台业务导航和实际页面路由必须同步新增。
- 需求说明使用 `PrdWrapper` 和 `prdNotes` 统一承载，交互区块尽量有对应需求标注。
- 新增或修改页面后至少执行一次 `pnpm build`。
- 交互验收至少覆盖：首次进入、筛选、空结果、创建、编辑、无变更取消、有未保存变更时取消、保存失败、批量操作、状态变更和返回路径。

## 10. 验收清单

### 页面与导航

- [ ] 页面在正确的业务分组下可见。
- [ ] 当前页面导航高亮，标题和页面树名称一致。
- [ ] 刷新或通过页面链接进入时，页面状态正确恢复。

### 列表与筛选

- [ ] 搜索、枚举筛选、重置均生效。
- [ ] 表格字段与业务需求一致，状态文案和颜色正确。
- [ ] 空结果、无数据、加载和错误状态可识别。
- [ ] 单条操作和批量操作的选择范围明确。

### 表单与弹窗

- [ ] 必填字段、格式、唯一性和数字范围校验有效。
- [ ] 保存成功、保存失败、取消和关闭行为符合预期。
- [ ] 独立新建/编辑页的“取消/保存”位于页面标题区右上角，且没有单独的“返回列表”按钮或底部重复操作区。
- [ ] 无未保存修改时点击取消直接返回列表；存在未保存修改时点击取消会提供“保存并返回”“不保存并返回”和“继续编辑”三种明确选择。
- [ ] 危险操作均有二次确认，且确认文案说明后果。

### 交付与工程

- [ ] 主要交互在桌面宽度下无横向溢出。
- [ ] 关键按钮具备键盘可达性和可读的文字标签。
- [ ] 页面数据、页面树、导航和 PRD 标注没有遗漏。
- [ ] `pnpm build` 构建通过。
